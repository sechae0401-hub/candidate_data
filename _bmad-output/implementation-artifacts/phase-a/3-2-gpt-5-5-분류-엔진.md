# Story 3.2: GPT-5.5 분류 엔진

Status: review

## Story

채매니저로서,
취소 대상 행이 자동으로 3건씩 분류되어 1차 원인·2차 행동·세부 태그 등 6개 항목이 추출되고, 빈 행은 자동 처리되길 원한다,
그래야 40~60건을 5분 안에 일괄 분류할 수 있다.

## Acceptance Criteria

1. **[3건 배치 분류]** `POST /api/classify` 요청은 최대 3건씩 처리하며 각 행에 대해 1차 원인, 2차 행동, 세부 태그, 타 과정명, 판단 근거, 검토 필요 여부를 JSON으로 반환한다. (FR20)
2. **[신규 카테고리 저장]** GPT가 기존 카테고리로 설명할 수 없는 사유를 반환하면 `new_categories` 테이블에 신규 카테고리명과 발생 건수가 저장된다. (FR21)
3. **[빈 행 자동 태깅]** 인터뷰내용과 특이사항이 모두 비어 있는 행은 GPT 호출 없이 `needs_review: true`, 1차 원인 "정보 부족"으로 저장된다. (FR22)
4. **[배치 실패 복구]** GPT API 호출이 공통 인프라 재시도 후에도 실패하면 1.5초 후 1회 행/배치 레이어 재시도하고, 그래도 실패하면 해당 배치 3건을 검토 필요로 저장한 뒤 다음 배치가 계속될 수 있게 응답한다. (FR23, NFR2)
5. **[성능/제한]** 50건은 5분 이내 처리를 목표로 하며, 200행 초과 요청은 시작하지 않는다. (NFR1, NFR5)
6. **[Vercel 타임아웃]** `/api/classify`에 9초 실행 제한 설정이 반영된다. (NFR2)

## Dev Notes

### 이전 Story에서 이어받는 맥락

- Story 3.1의 `/analyzing` 화면은 `classification_draft` payload를 읽고 3건씩 `/api/classify`를 호출한다.
- `src/upload/classification-draft.ts`의 `ClassificationDraftRow`는 `rowIndex`, `interviewContent`, `notes`, `resultValue`, `source`를 포함한다.

### 이번 Story의 핵심 제약

- feedback Rule 1: `/api/classify`에서 `runWithGptRetry`를 직접 호출하지 않는다. 공통 OpenAI 래퍼(`runOpenAiJsonRequest`)를 쓰고, 행/배치 레이어 1.5초 후 1회 재시도는 별도 함수로 감싼다.
- GPT 응답은 Responses API의 `output_text`에서 읽고 Zod로 검증한다.
- 빈 행은 GPT 비용을 쓰지 않고 즉시 "정보 부족" 검토 필요로 처리한다.
- Route Handler는 요청 본문을 Zod `safeParse`로 검증한다.
- 서버 전용 비밀키는 브라우저에 노출하지 않는다.
