# Story 4.1: 분류 결과 테이블 및 요약 바

Status: done

## Story

채매니저로서,
분류 결과 전체를 검토 필요·완료 상태별로 구분된 테이블로 한눈에 확인하고 싶다,
그래야 어떤 건을 먼저 검토해야 하는지 즉시 파악할 수 있다.

## Acceptance Criteria

1. **[요약 바]** `/result` 페이지 상단에 "전체 N건 | 검토 필요 M건 | 완료 K건" 요약 바가 표시된다. (FR25, UX-DR6)
2. **[결과 테이블]** 각 행에 행번호, 인터뷰 내용 요약, 1차 원인, 2차 행동, 세부 태그, 타 과정명, 판단 근거, 검토 필요 여부가 표시된다. (FR26)
3. **[검토 필요 행]** `needs_review: true`인 행은 `#FFFBEB` 배경 + 왼쪽 4px amber 선으로 표시되고 "검토 필요" 배지가 표시된다. (FR27, UX-DR10, UX-DR11)
4. **[완료 행]** `needs_review: false` 또는 `review_completed: true`인 행은 `#F0FDF4` 배경 + 왼쪽 4px emerald 선으로 표시되고 "완료" 배지가 표시된다. (FR27, UX-DR10, UX-DR11)
5. **[테이블 밀도]** 클릭 가능한 행은 최소 48px 높이를 유지하고 셀 패딩은 `px-4 py-3`이다. (UX-DR16)
6. **[원문 데이터 준비]** 결과 조회 데이터에는 인터뷰 내용과 특이사항 원문이 포함되어 이후 Story 4.2 원문 패널에서 재사용할 수 있다. 기존 데이터에 원문이 없으면 안전한 fallback을 표시한다.

## Dev Notes

### 이전 Story에서 이어받는 맥락

- Story 3.2는 `POST /api/classify`에서 `classification_results`와 `new_categories`를 저장한다.
- Story 3.3은 `sessions.insight_summary`를 JSON 문자열로 저장하고 `sessions.status = completed`로 업데이트한다.
- Story 3.4는 `GET /api/result/[sessionId]`를 준비했고, 현재 결과 화면은 골격만 존재한다.

### 이번 Story의 핵심 제약

- 서버 전용 DB 접근은 Route Handler와 `src/shared/supabase/server.ts`를 통해서만 수행한다.
- Supabase 조회에서 `select("*")`를 쓰지 않는다. 필요한 컬럼만 명시한다.
- 원문 데이터 컬럼은 nullable로 추가해 기존 테스트/기존 세션이 깨지지 않게 한다.
- `src/result/`는 결과 화면 전용 순수 로직과 클라이언트 UI를 둔다. `upload`, `classify` 모듈을 직접 import하지 않는다.
- 화면은 업무용 도구 톤을 유지한다. 카드 중첩을 피하고, 테이블은 고밀도지만 행 클릭 영역 48px 이상을 지킨다.
